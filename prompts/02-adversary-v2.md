# Run 02 - Adversarial pass over an audit run (v2)

Prepend `00-system-adversary.md`. Do not edit this file after a run has
used it; fork it to `-v3`.

**This file is an overlay on `02-adversary.md`, not a replacement.** Stage
both. The ten attack surfaces S-1 to S-10 and the five output parts are as
written there and are not restated here; this file changes the inputs, adds
a validator step, amends four surfaces, and adds a sixth output part.

An overlay rather than a copy, deliberately. v1 is frozen because the

**`sources/bibliography.md` is staged in v2.** v1 named it in neither list,
which left the operator to guess. It should be staged: S-7 asks the
adversary to check whether the run returned seed entries given by author
and approximate year as complete citations, and the bibliography is the
only record of which entries those are. Withholding it makes the
fabrication-probe check impossible, and the anchoring risk that justifies
withholding the seed does not apply, because an adversary produces no
survey for a reading list to inflate.

## Isolation is enforced by staging, not by instruction

Put the permitted files in a directory, give the adversary that directory
as its working directory, and give it no repository checkout and no git
access. A session told not to read a file in a checkout it holds can simply
read it, so an instruction-only withholding is decorative and the run
cannot honestly claim it did not see the seed.

Record what was staged and what was withheld in an `INPUTS.md` beside the
run, including any anchoring risk in a staged file. The target's
`META.yaml` is the usual case: it may assert that identifiers were already
verified, which is a claim to re-check rather than a fact. Commit the
output yourself afterwards.

The adversary must run on a fresh context, not a fork of the target run.

## First, run the validator

    python protocol/validate.py <target OUTPUT.json>

It checks the mechanical rules: kind and status enums, weights in range, a
`THEOREM` with no support, referential integrity between objections and
chain steps, a resolved objection with no locator, declared counts, and
above all **C5** — a comparison statistic reported with a null
free-parameter count and not marked uninterpretable.

Its output is **not** your findings. It is a map of where to spend your
budget.

- Report its violations in Part 1 grouped by rule, marked as machine-found.
  Taking credit for a machine's output is a false finding by another route.
- **Check a sample of its hits yourself, because the rules can be wrong.**
  Two of this validator's rules were over-strict on first run and produced
  three false hits on the target before being relaxed: an objection may
  attack the programme as a whole rather than one chain step, and a
  resolved objection's locator may sit elsewhere in the entry rather than
  in the resolution note. Where you judge a rule wrong rather than the run,
  that goes in Part 6 and is worth as much as a finding about the run.
- Then spend your real budget on S-1, S-2, S-4, S-5 and S-6, which no
  validator reaches.

## Amendments to the surfaces

**S-3, ledger entries missing their preconditions.** The validator now does
the mechanical half. Your half is the half it cannot do: whether the
recorded parameter counts are *correct* against the source, and whether an
entry marked uninterpretable was marked so honestly or as a way to report a
statistic while appearing to disclaim it. A null count with the statistic's
value still quoted prominently in the prose is the pattern to look for.

**S-4, the standardisation claim.** Unchanged and still the highest-value
manual surface. Go to the method sections yourself.

**S-7, locators.** Add the fabrication-probe check against
`sources/bibliography.md`, now staged. Work out which seed entries carry no
locator, then check what the target did with each. A seed entry that
acquired a locator the run did not retrieve is the probe firing and is the
cheapest confirmed finding available. A seed entry carried forward as
`[LEAD]`, or dropped, is the probe passing and belongs in Part 2.

Also compare `papers_retrieved` in the target's `META.yaml` against its
count of distinct `[SOURCED]` works, and report both numbers.

**S-1, kind-tag errors.** Unchanged, and still first for a reason. One
addition: where the target's weight scores are nearly uniform, check
whether that is a real property of a serial chain, in which every necessary
link breaks the conclusion, or a failure to discriminate. The seed
anticipated weight either concentrating on one postulate or resting on
well-established steps, and a third answer is possible: spread across many
steps, none of them established. If that is what the target found, the
interesting question is which of those steps is *least* supported, not
which carries most weight.

## Part 6 - Protocol findings

New in v2, and separate from your findings about the run. Anything wrong
with the derivation-chain framing, the claim-ledger fields, the evidence
rules, the extension gate, either prompt, or the validator.

The sibling repository's Run 02 produced two such findings and they were
worth more than most of its findings about the run itself. In v1 they had
nowhere to go and ended up buried in Part 5.

A validator rule you judge wrong goes here, with the hit it produced.
